Problem Statement

Current city-wide public health advisories are too generic and fail to drive behavioural change in specific high-risk neighbourhoods. Seasonal heat events disproportionately affect elderly, low-income, and high-density communities — yet all areas receive the same communication. This leads to missed high-risk areas, wasted field resources, and reduced communication effectiveness.

Project Objective

Build a decision-support system (not a replacement for clinical or departmental judgement) that identifies neighbourhood-level heat risk using temperature, built-environment, service-access, and aggregate vulnerability indicators, then recommends timely, understandable communication and response actions.

Architecture

Frontend: HTML5 + Bootstrap 5 + Chart.js + Leaflet.js
Backend: Python 3.10+ / Flask 3.0
Database: SQLite (via sqlite3 — no ORM)
Data: Pandas + NumPy (generate_data.py)
ML/Risk: Transparent weighted formula (risk_engine.py)
Map: OpenStreetMap + Leaflet.js (no API key required)

Dataset

60 synthetic neighbourhoods generated by generate_data.py with fields covering climate (temperature, humidity, heat index), demographics (population, elderly %, child %, low income %), built environment (green space, building density), service access (healthcare facilities, cooling centres, transport, nearest hospital), composite scores, and risk classification.

5 edge-case neighbourhoods are explicitly injected: missing temperature, conflicting indicators, no cooling/healthcare, extreme outlier temperature, and override-disagreement seed.

Risk Calculation

Heat Risk Score =
  (Climate/Heat Index normalised) × 0.35
+ (Vulnerability Score normalised) × 0.30
+ (Built Environment Risk normalised) × 0.20
+ (Service Access Risk normalised) × 0.15

× 100 → Range: 0–100

Thresholds: 0–39 = Low | 40–69 = Medium | 70–100 = High

All component contributions are shown on every neighbourhood detail page so health officers can understand and challenge any score. The model is never a black box.

Hard Constraints

  • HC-01: Aggregate neighbourhood data only — no individual records
  • HC-02: High-risk neighbourhoods cannot be auto-closed
  • HC-03: High-risk classifications require human review
  • HC-04: Emergency cases (score ≥ 90) must be escalated
  • HC-05: Only Health Officers/Administrators can override
  • HC-06: Override requires written reason
  • HC-07: Every override is permanently logged with full details
  • HC-08: Missing temperature or vulnerability data blocks auto-classification

Soft Constraints

6 configurable priorities (SC-01 through SC-06) allow authorised staff to tune response strategy using sliders on the Constraints page. Changes are audited.

Human Review

Every High-risk and AMBIGUOUS classification automatically creates a Review Queue entry. Officers can Approve, Modify, Escalate, or Request More Information. All decisions are logged.

Override Mechanism

Health Officers and Administrators can override risk levels with mandatory written reason. The override is written to the overrides table and the audit_logs table simultaneously. The Audit Log page shows all overrides with user, timestamp, original and new value, and reason.

Escalation Logic

Five escalation paths: Low (monitor), Medium (field officer + monitor), High (Health Officer + urgent comms + field), Ambiguous (manual review), Emergency (auto-escalate, score ≥ 90). See the Escalation page for the visual flow.

Baseline Comparison

Baseline = generic city-wide advisory (equal treatment of all neighbourhoods, 50% effective reach estimated). Proposed = neighbourhood-targeted strategy. Metrics calculated from generated dataset — not hard-coded.

Experiment

Run experiment.ipynb for full EDA, indicator analysis, risk score calculation, baseline vs. proposed comparison, objective charts, measured metrics, and error analysis.

Failure Cases

5 failure cases: FC-01 (missing data), FC-02 (conflicting indicators), FC-03 (no services), FC-04 (extreme outlier), FC-05 (override disagreement). All handled via detection → human review → escalation.

Setup Instructions 

# 1. Install dependencies
pip install -r requirements.txt

# 2. Generate synthetic dataset
python generate_data.py

# 3. Start the application (auto-inits database)
python app.py

# Open: http://127.0.0.1:5000
# Login: admin / admin123

Application Workflow

1. Synthetic Neighbourhood Data (generate_data.py)
→ 2. Data Validation (hard constraint checks)
→ 3. Risk Score Calculation (transparent weighted formula)
→ 4. Risk Classification (Low / Medium / High / AMBIGUOUS)
→ 5. Communication Recommendation (channel + message by risk level)
→ 6. Human Review Queue (mandatory for High + AMBIGUOUS)
→ 7. Authorised Override (Health Officer / Admin, reason required, logged)
→ 8. Escalation (automatic for emergencies, manual for review queue)
→ 9. Communication / Field Action (sent and recorded)
→ 10. Outcome Tracking (audit log, communication history)
→ 11. Experiment Metrics (Experiment Results page + notebook)
